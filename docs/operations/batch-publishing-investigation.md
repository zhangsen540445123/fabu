# 三平台拆分扣次排查（2026-11-07）

## 已确认的原因

1. 既有 `build_local_payloads` 为每个目标生成独立 payload；CLI gateway/coordinator 逐目标调用 `publish`。
2. 2026-11-07 经明确授权的独立CLI联调分别执行三次投稿，获得三个不同 taskSetId。客户端各显示“1账号·1任务”，免费发布次数由0/3变为3/3。
3. 用户手动一次选择三个账号的历史发布显示一个任务组内“3账号·3任务”，用户报告其消耗一次免费次数。必须区分任务组数量和组内平台任务数量；不能根据UI中“3任务”推断扣3次。
4. 不是视频上传了三次：联调视频和封面各上传一次，三个投稿复用同一资源。问题发生在创建发布任务组这一层。

## 本机CLI离线验证

安装版本3.2.32；使用无效合成凭证、明确的非真实媒体Key及账号ID，服务地址固定127.0.0.1:1。本轮没有真实上传、投稿或创建云端草稿。

| 检查 | 实际结果 |
| --- | --- |
| 单平台 publish --dry-run 对照 | 通过 |
| publish 的平台参数包含三个逗号分隔平台 | 拒绝：publish supports exactly one platform per command |
| 单平台参数 + payload.platforms包含三个平台 | 拒绝：/platforms: exactly one platform is required |
| draft save --dry-run，三个平台及三份accountForms | 通过，输出仍有三个平台、三份账号表单及共享媒体，isDraft=true |

官方公开源码 `cmd/publish.go` 将命令定义为“单平台原子发布”；`internal/workflows/publish/service.go` 调用SinglePlatform并将platforms收敛为单元素数组，与本机二进制实测一致。

## 尚未验证，不能当作已经解决

- `draft save --dry-run` 不访问真实服务，不能证明服务端接受多平台草稿，也不能证明客户端能无损恢复这些字段。
- 草稿保存不是正式发布；当前CLI没有在help中公开“多平台一次提交”或“按草稿ID直接发布”的命令。
- 不能把draft标志删掉后借草稿接口发正式任务；不能私自修改官方二进制或绕过现有费用/重复提交保护。
- 三平台合并发布的实际扣次必须在用户另行授权的下一条视频上观察发布前后余额；不得重新投稿已存在的当前视频。

## 待选择的替代路线

推荐优先验证“CLI一次生成/保存三平台草稿 + 客户端一次合并提交”。通过后再将客户端步骤接入自动化；这样复用既有账号配置与平台字段校验，但新增客户端UI依赖，需要明确确认此技术路线变化。

若草稿恢复不兼容，则使用客户端批量发布页面直接导入本地成片、封面和三个账号参数，最终只提交一次。这比继续拆分CLI更符合目标，但应对客户端UI变更、登录/验证码、上传完整性增加检查。

纯CLI全自动合并发布没有验证通过。在用户选择替代路线并完成验证前，保持真实自动投稿禁用，不宣称“一键只扣一次”已修复。

## 下一步验收标准

- 一份共享媒体/标题的逻辑发布仅有一个任务组ID，组内有三个精确账号ID。
- 每个平台自己的标签、分类、来源声明和可见性保持不变，不跨账号错误复用。
- 最终提交前核对三个账号与本机发布通道；失败/超时不自动降级成三次独立投稿。
- 重启和超时后沿已知任务组只读对账，不重复提交。
- 用量前后差为1的实测才能确认节省额度；dry-run/模拟测试不能替代。
- 发布成功还需核对各平台内容时长，不能以提供方success代替完整成品验收。
