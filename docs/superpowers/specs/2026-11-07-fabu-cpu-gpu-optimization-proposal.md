# Fabu CPU + GPU 协同处理优化方案（讨论稿）

日期：2026-11-07。状态：方案待确认；未接入硬件编码、未测速、未修改当前任务。当前CPU任务已于15:04:30自然完成并通过完整校验。

## 1. 目标与边界

- 用户要求 CPU 与显卡协同处理，改善 2K/H.265 导出速度；后续继续支持可编排视频处理。
- 当前进行中的任务必须按原始冻结预设完成。不停止进程、不重启应用、不改驱动或工具、不并行跑编码测速。
- 保留 2560×1440、30fps、yuv420p、音画同步及完整性校验。不通过删校验、隐式降画质、切换来源或发布状态提速。
- 不新增付费服务，不调用云转码。本次仅方案，不代表 GPU 能力或加速倍率已验证。
- 后续性能测试为开发验收，不恢复每个任务强制人工确认样片。

## 3. 推荐架构：CPU / GPU 分工，而非分别编码半段后拼接

### 路线 A：通用混合流水线，第一期优先

```text
源文件
  → CPU 解码
  → CPU 单一滤镜图（裁剪、调色、字幕、片头片尾、时间线等）
  → 帧传入显卡
  → GPU NVENC H.265 编码
  → 合并 CPU 处理的音轨
  → 独立完整校验
  → 成片 READY
```

保留现有滤镜语义，先替换最明显的 CPU 编码负担。CPU 与硬件编码器在同一流式任务中分工，不为每个处理步骤生成、重编码一个中间 MP4。是否由 CPU 滤镜成为新瓶颈，由分阶段数据判断。

### 路线 B：简单任务 GPU 快速通道，第二期

```text
GPU 硬件解码 → GPU 缩放 → GPU H.265 编码
CPU：调度、音频、文件管理、独立校验
```

面向当前这种仅调整分辨率的任务。只在输入解码能力、像素格式、色彩、旋转/SAR、缩放算法和时间戳行为均已验证时启用；不能仅根据“步骤数为零”判定。当前二进制可见 scale_cuda，未见 scale_npp，不把文档示例中的 NPP 视为本机已具备。

### 路线 C：保留 CPU 基线与兜底

保留现有 libx265 输出，供对照、特殊源兼容以及无硬件编码环境使用。CPU 的更快预设是另外的质量/体积选择，不在本轮默认降低规格。

第一期只调度 Ryzen CPU + NVIDIA 独显；不引入 AMD 集显与 NVIDIA 独显之间的多设备调度，避免增加未经验证的设备选择和帧传输组合。

## 4. 自动选择规则

1. 解析源和预设，检查已验证的本机能力。
2. GPU 不可用：任务启动前，依据用户明确设置的兜底策略选择 CPU，并在界面说明原因。
3. 硬件编码可用且整个视频图属于 GPU 快速通道白名单：选择路线 B。
4. 有字幕、复杂合成或任何未经验证的 GPU 步骤：选择路线 A。
5. 把最终 encoder、设备、质量参数、执行路径和滤镜图写入不可变执行计划，再开始任务。

约束：
- GPU 探测结果应按 FFmpeg 文件哈希、驱动版本、设备身份和探测配置缓存；变更后重新验证。
- 区分“存在显卡”“FFmpeg 列出了编码器”“初始化成功”“真实媒体编码通过”四层状态。
- 当前任务运行中不做驱动更新，不热替换 FFmpeg。
- 禁止编码到一半默默换后端并混用旧计划摘要。运行期 GPU 失败先安全暂停；后续重编译/重试必须创建新执行尝试，保留源缓存和错误记录。
- 自动模式是任务开始前选路，不是修改已经冻结的用户预设。

## 5. 质量与格式策略

- 首期保持 H.265、2560×1440、30fps、yuv420p、既有色彩与音频契约。
- CPU 使用 CRF；NVENC 使用其支持的独立码率控制配置。不把 CRF20 机械翻译成 CQ20 并声称等质。
- 候选质量档：均衡、画质优先、速度优先；具体 preset/CQ/码率上限以本机和素材测试后确定。
- GPU 缩放与 CPU 缩放必须分别核对插值、取样、色彩范围、旋转、SAR 与字幕位置。若结果不满足同一预设语义，就保留 CPU 滤镜，不偷偷变更。
- 音频留在原音频链；没有经过等价性验证前不默认 stream-copy，避免变速、淡入淡出、时间戳规范化等行为被绕开。
- H.264 可作为后续独立输出选项，但不为了本轮提速擅自改变当前 H.265 输出及验证契约。

## 6. 调度与校验优化

- 初期仍保持单任务重处理，不同时跑多个导出来制造 CPU/GPU/磁盘争用。
- CPU 滤镜线程数以 4/6/8 等少量候选实测；不盲目用满 16 逻辑线程，不修改当前 x265 参数。
- 连续兼容滤镜编译为同一个 FFmpeg 图，正常路径只做一次最终有损编码。
- 尽量把 CPU 步骤集中执行，避免同一帧频繁在 CPU/GPU 间往返。
- 界面拆分“源校验 / 渲染 / 输出校验”，分别计时；渲染达到 99% 不等于整个任务已经完成。
- 首期保留完整输出校验。后期单独评估复用不可变源的有效校验证据，或把重复扫描合并；必须保留逐帧几何/数量、时间戳、整段视频与音轨解码的等价覆盖，不能改成只抽检开头中间结尾。
- 不把 NVENC 单独的 fps 当端到端速度，记录下载外的准备、滤镜/编码、验证和总耗时。

## 7. 测试与验收（当前任务完成后再开始）

### A. 能力试验

使用独立临时目录及合成短视频测试 NVENC 初始化、所需格式、GPU 解码与 scale_cuda。限制时长、超时和输出体积。驱动不匹配时明确报告；未经用户确认不安装或更新驱动。

### B. 同源对比

选当前已下载原片中的代表性片段，总计约 30～60 秒，包含头发/胡须细节、皮肤渐变与较快动作。串行运行：

| 组别 | 用途 |
| --- | --- |
| CPU libx265 / fast / CRF20 | 保留基线 |
| CPU 滤镜 + NVENC 均衡配置 | 第一期建议路径 |
| GPU 解码 + GPU 缩放 + NVENC | 简单任务快速通道 |

记录编码/总耗时、fps、CPU 占用、GPU Video Encode/Decode 使用、峰值内存/显存、输出大小、同步/时长/格式、细节与色带。只在工具支持时记录硬件遥测；不能把 3D 使用率当编码器利用率。

画质指标以同一份未经有损编码的目标分辨率参考帧比较两条编码路径；CPU 的有损成片不是绝对真值。可结合客观指标与局部视觉检查，不能仅凭文件小或分数高宣称画质等价。复杂流水线另加字幕、调色、变速、片头片尾回归，不以纯缩放成绩替代。

### C. 性能目标与算例

本机采样约 0.32x。以下仅是条件算例，不是 GTX 1650 的测速结果或承诺：
- 713 秒视频若达到 1x，编码约 11.9 分钟。
- 若达到 2x，编码约 5.9 分钟。
- 端到端时间还包括准备及完整校验。

建议第一期以“同源混合路径编码时间显著低于 CPU 基线；目标不超过其 50%，并保持质量验收”作为试验目标。若不达标，按实际瓶颈调整，不为了达标偷偷降低分辨率/帧率/质量。

### D. 自动化门槛

- CPU / NVENC 配置 schema、参数互斥、计划摘要和旧预设兼容测试。
- 故障：驱动不兼容、设备不可用、显存不足、取消、磁盘不足、工具/源变更。
- 无 GPU 的 CI 通过合成能力与命令测试；本机硬件验收独立记录，不能用 mock 通过冒充。
- 两种模式均保留完整源/输出检查；本地任务无需新增人工样片门槛；不触发发布。

## 8. 建议开发批次

1. 能力探测 + 本机短片对比报告：先证明可用、有收益。
2. 编码后端拆分：新增 NVENC 参数模型和通用混合执行路径；保留 CPU。
3. GPU 快速通道：简单流程白名单及等价性回归。
4. 产品化：界面显示实际设备/路径/阶段耗时；自动策略和明确兜底原因。
5. 独立优化验证阶段：仅当数据表明其成为主要耗时，再做等价合并或证据复用。

拟涉及路径：
- 新增 `src/fabu/media/hardware.py`：只读发现及受控能力测试。
- 新增 `src/fabu/media/encoders.py`：CPU/NVENC 命令参数构建。
- 扩展 `models.py`、`compiler.py`、`baseline.py`、`renderer.py`、`runtime.py`、`validator.py`。
- 扩展 presets、任务阶段/能力 API、预设与任务页面、media 单元/集成及前端 E2E 测试。
- 不绕开现有工具身份、不可变源、计划绑定、发布审批和目标授权边界。
