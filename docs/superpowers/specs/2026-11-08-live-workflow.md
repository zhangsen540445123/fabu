# 自动真实发布工作流设计

用户已确认目标：链接+标题 → 默认预设/默认发布配置 → 下载校验 → 处理校验 → 上传 → 三个平台分别提交 → 跟踪结果。

## 边界
- 复用 Python/FastAPI、SQLite 单工作进程、React 与固定版本官方 CLI，不另起一套投稿脚本。
- 默认作用于之后明确创建的自动流程；不自动恢复、重发现有冻结任务，不凭历史任务标题生成新投稿。
- 桌面启动始终读取真实安装的同一状态/配置/数据库。禁止通过重建数据解决路径不一致。
- 实际传输显式 local 通道、固定客户端身份，禁止 cloud 发布回退、支付/充值/订购命令。
- 接受单个平台一个任务，三平台最多三次。保守本地日额度账本（北京时间）不是官方剩余额度；外部手动发布可能导致官方拒绝，拒绝时暂停，不支付、不盲目重试。
- 用户作业执行许可与平台能力验收证据分开。既有能力 UNKNOWN 不伪造为已验证；新的自动真实流程依赖显式作业授权、身份锁定、活动账号、资源校验、来源声明、保守次数预算。
- 先接通默认立即发布；平台原生预约仍执行既有窗口验收约束，不把本地定时或立即回退伪装成原生预约。
- 每次副作用前持久化；有完整接受回执的一个目标不阻止另两个不同目标提交。超时/不明结果不重发，重启只恢复只读跟踪。
- 上传回执验证官方 bucket/key、大小、宽高、时长；接受真实 yfb/ key，不因前缀错误误判。不能以本地验证代替平台成片验证。
- 独立记录 provider 状态和平台/质量验证状态，provider success 不标为平台完整成片通过。B站2秒故障未根因修复前如实显示风险。
- 真实端到端验收必须用用户明确选定的新链接/标题，不使用已发布素材重发来消耗额度。

## 组件
1. 启动和配置一致性：调查当前后台误读，补回归测试，安全切换服务。
2. 本地执行策略：受保护配置、二进制与客户端绑定、每作业最多2次上传/每账号1次提交、本地每日3次预算。
3. 协调器：真实队列/自动handoff、用户作业许可、已接受回执与未知副作用分离、可诊断暂停原因。
4. 跟踪器：有界只读轮询、持久化脱敏provider观察，重启后恢复，展示结果不冒充验证。
5. 界面：动态运行就绪状态、默认自动流程、阶段状态、真实/仿真区分与风险提示。

## 验收
自动测试使用确定性CLI替身+真实本地合成媒体，不访问外部发布；覆盖下载→处理→两个上传→三个唯一提交→跟踪、错误停止、重启/重复保护。运行实例API读到既有配置和1条历史冻结任务。真实联调另行记录，未执行不宣称已通过。
